# 自动保存架构重构设计

## 📋 背景与问题

### 当前架构问题

现有的 `autoSave.ts` 采用**单一防抖策略**处理所有状态保存，存在以下问题：

#### 1. **缓存不同步问题**
```
用户操作：关闭标签页
↓
menuStore.delVisitedView() → 从内存删除
↓
markDirty() → 标记需要保存
↓
防抖 3 秒后才写入 states.dat
↓
❌ 用户立即重新打开该页面 → 读到旧缓存
```

#### 2. **性能浪费**
```typescript
// 当前实现：任何改动都保存全部状态
const newState = {
  visitedViews: [...],      // 改了快捷键也要保存标签页？
  cachedViews: [...],
  activeRoute: "...",
  pageStates: {...},
  sqlMetadata: {...}
};

const newPreferences = {
  sqlShortcuts: {...},      // 改了主题也要保存快捷键？
  elfkShortcuts: {...},
  monitorDefaults: {...},
  esSearchPrefs: {...},
  uiPrefs: {...}
};
```

#### 3. **逻辑耦合严重**
- 23 个地方调用 `markDirty()`
- 无法区分什么操作该用什么保存策略
- 新增保存类型需要修改核心逻辑

#### 4. **无法精细控制**
- 标签页删除应该**立即保存**（用户期望实时生效）
- 页面快照可以**防抖保存**（避免频繁写入）
- 偏好设置应该**独立保存**（不影响其他状态）

---

## 🎯 重构目标

### 核心原则
1. **职责单一** - 每个管理器只负责一类状态的保存
2. **策略独立** - 不同类型的状态有不同的保存策略
3. **立即生效** - 关键操作（标签页）立即保存，不防抖
4. **性能优化** - 只保存变更的数据，不打包无关状态
5. **加密透明** - 所有数据通过 Rust 端 AES-256-GCM 加密，Manager 层无需关心

### 预期效果
- ✅ 关闭标签页后立即保存，重新打开不会读到旧缓存
- ✅ 修改快捷键只保存偏好设置，不触发标签页保存
- ✅ 页面快照防抖 3 秒，避免频繁写入
- ✅ 代码清晰，新增保存类型只需添加新 Manager
- ✅ 加密过程完全透明，业务代码只处理明文 JSON

## 🔐 加密机制说明

### 数据流转过程

```
业务代码（明文 JSON）
  ↓
Manager 构建数据对象
  ↓
scheduler.schedule(type, dataBuilder)
  ↓
scheduler.executeSave(type)
  ↓
scheduler.writeToStorage()
  ↓
saveStorageDataAsync(file, data)
  ↓
┌──────────────────────────────────────────────┐
│  core.ts（存储核心层）                        │
│  1. 更新内存缓存（明文）                      │
│     memoryCache.set(file, data)               │
│  2. 序列化为 JSON 字符串                      │
│     const jsonStr = JSON.stringify(data)      │
│  3. 调用 Rust 端异步保存                      │
│     invoke('save_store_async', {              │
│       file,                                   │
│       plaintext: jsonStr                      │
│     })                                        │
└───────────────────┬──────────────────────────┘
                    ↓
┌──────────────────────────────────────────────┐
│  Rust 端（src-tauri/src/commands.rs）         │
│  1. 接收明文 JSON 字符串                      │
│  2. 调用 crypto::encrypt() 加密               │
│     - AES-256-GCM 算法                        │
│     - 使用设备密钥（device_key）               │
│     - 生成随机 nonce（12 bytes）               │
│     - 组合：nonce + ciphertext → base64       │
│  3. 写入 Tauri Store 文件                     │
│     store.set("data", encrypted)              │
│     store.save()                              │
└──────────────────────────────────────────────┘
```

### 加密细节

#### 加密算法
- **算法**: AES-256-GCM（认证加密）
- **密钥**: 设备密钥（device_key），绑定到当前设备
- **Nonce**: 随机生成 12 bytes，每次加密不同
- **输出格式**: `base64(nonce + ciphertext + auth_tag)`

#### 加密代码（Rust 端）
```rust
// src-tauri/src/crypto.rs
pub fn encrypt(plaintext: &str) -> Result<String, String> {
    let key_bytes = get_device_key()?;  // 获取设备密钥
    let key = Key::<Aes256Gcm>::from_slice(&key_bytes);
    let cipher = Aes256Gcm::new(key);
    
    // 生成随机 nonce (12 bytes)
    let mut nonce_bytes = [0u8; 12];
    rand::thread_rng().fill(&mut nonce_bytes);
    let nonce = Nonce::from_slice(&nonce_bytes);
    
    // 加密
    let ciphertext = cipher.encrypt(nonce, plaintext.as_bytes())?;
    
    // 组合 nonce + ciphertext，然后 base64 编码
    let mut combined = nonce_bytes.to_vec();
    combined.extend(ciphertext);
    Ok(BASE64.encode(&combined))
}
```

#### 异步保存流程
```rust
// src-tauri/src/commands.rs
#[tauri::command]
pub async fn save_store_async(
    app_handle: AppHandle,
    file: String,
    plaintext: String,  // 明文 JSON
) -> Result<(), String> {
    use tauri_plugin_store::StoreExt;

    // 1. 加密
    let encrypted = crypto::encrypt(&plaintext)?;

    // 2. 写入 store 文件
    let store = app_handle.store(&file).map_err(|e| e.to_string())?;
    store.set("data", serde_json::Value::String(encrypted));
    store.save().map_err(|e| e.to_string())?;

    Ok(())
}
```

### 对重构的影响

#### ✅ 透明加密，无需修改
由于加密完全在 Rust 端处理，**新架构无需关心加密逻辑**：

```typescript
// Manager 层只需要构建明文数据
scheduler.schedule(SaveType.TAB, () => {
  return {
    visitedViews: [...],  // 明文对象
    cachedViews: [...],
  };
});

// scheduler 调用 core.ts
saveStorageDataAsync('states.dat', { admin: data });
// ↑ 这里会自动：
// 1. JSON.stringify(data) → 明文 JSON 字符串
// 2. invoke('save_store_async', { file, plaintext })
// 3. Rust 端加密并写入文件
```

#### ⚠️ 注意事项
1. **没有压缩** - 当前实现只加密不压缩，大体积数据（如 SQL 元数据）需注意
2. **并发安全** - Rust 端的 `store.save()` 是同步操作，多次调用会串行执行
3. **内存缓存** - `memoryCache` 存储的是明文数据，退出登录时必须清除

#### 💡 未来优化空间
如果需要进一步减小文件体积，可以在 Rust 端添加压缩：
```rust
// 伪代码：加密前压缩
use flate2::Compression;
use flate2::write::GzEncoder;

pub fn encrypt_and_compress(plaintext: &str) -> Result<String, String> {
    // 1. 压缩
    let mut encoder = GzEncoder::new(Vec::new(), Compression::default());
    encoder.write_all(plaintext.as_bytes())?;
    let compressed = encoder.finish()?;
    
    // 2. 加密
    encrypt(&String::from_utf8(compressed)?)
}
```

**当前阶段不需要实现压缩**，先完成架构重构即可。

### 问题现象
用户反馈：**每次加载缓存（启动应用/重新登录）时感觉很慢**

### 完整加载流程分析

让我们追踪一次完整的启动流程，看看时间都花在哪里了：

### 性能瓶颈拆解

#### 📌 重要发现：串行加载是有原因的！

你说得对，**数据加载确实有依赖关系**，不能简单地并行化。

让我分析完整的依赖链：

```
│ - 5 个文件之间**没有依赖关系**                          │
│ - 每个文件独立解密                                      │

                        ↓

│                                                         │
```

#### 瓶颈 1️⃣：文件解密（**可优化**）⏱️ 200-500ms

**位置**：`core.ts` → `initAllStorage()`

```typescript
export async function initAllStorage(): Promise<void> {
  const files = [
    'app.dat',
    'tokens.dat',
    'profiles.dat',
    'states.dat',        // ← 可能最大（包含标签页、快照、SQL元数据）
    'preferences.dat',
  ];

  // ❌ 串行解密：一个接一个
  for (const file of files) {
    const data = await loadAndDecrypt(file);  // ← 每个文件都要：
    // 1. Tauri Store 读取文件
    // 2. invoke('decrypt_data') → Rust 解密
    // 3. JSON.parse()
    memoryCache.set(file, data);
  }
}
```

**时间分析**：
- 每个文件解密：50-150ms（取决于文件大小）
- 5 个文件串行：5 × 100ms = **500ms**
- `states.dat` 可能更大（包含 SQL 元数据缓存）：200-300ms

**Rust 解密性能**：
```rust
// crypto.rs → decrypt()
pub fn decrypt(encrypted: &str) -> Result<String, String> {
    // 1. Base64 解码：~5ms
    let combined = BASE64.decode(encrypted)?;
    
    // 2. AES-256-GCM 解密：~10-20ms（取决于数据大小）
    let plaintext = cipher.decrypt(nonce, ciphertext)?;
    
    // 3. UTF-8 解码：~2ms
    String::from_utf8(plaintext)
}
```

**结论**：
- ✅ Rust 解密本身不慢（10-20ms/文件）
- ✅ **5 个文件之间没有依赖关系** ← 你说的串行原因不在这里
- ❌ **串行加载是问题**（5 个文件排队）
- ❌ **IPC 调用开销**（JS → Rust 每次 invoke 约 5-10ms）

**为什么可以并行**：
```typescript
// 当前代码
core.ts → initAllStorage()
  ↓
  for (const file of files) {
    const data = await loadAndDecrypt(file);
    memoryCache.set(file, data);  // ← 各自写入独立的缓存
  }

// 每个文件独立：
// - app.dat → memoryCache['app.dat']
// - tokens.dat → memoryCache['tokens.dat']
// - profiles.dat → memoryCache['profiles.dat']
// - states.dat → memoryCache['states.dat']
// - preferences.dat → memoryCache['preferences.dat']
// ↑ 没有交叉依赖，可以并行！
```

#### 瓶颈 2️⃣：状态恢复（**必须串行，无法优化**）⏱️ 100-300ms

**位置**：`authStore.ts` → `initFromStorage()`

**这里的串行是正确的！因为有严格的依赖关系**：

```typescript

  await initAllStorage();  // ← 等 5 个文件都加载到内存
  
  // 第 2 步：从 tokens.dat 获取用户名
  const hasFileToken = hasValidToken();  // ← 读 tokens.dat
  const userName = getTokenUsername();   // ← 需要 tokens.dat 的数据

  const profile = getStoredProfile(userName);  // ← 读 profiles.dat[userName]
  const state = getState(userName);            // ← 读 states.dat[userName]
  const prefs = getPreferences(userName);      // ← 读 preferences.dat[userName]

  // 1. 先恢复主题（影响后续渲染）
  if (prefs?.theme) {
    useAppStore.getState().setTheme(prefs.theme);
  }
  
  // 2. 恢复用户偏好
  useUserPrefsStore.getState().restorePrefs({...});
  
  // 3. 恢复菜单状态（依赖主题已设置）
  if (state.visitedViews?.length) {
    menuStore.clearVisitedViews();
    state.visitedViews.forEach(v => {
      menuStore.addVisitedView(v);  // ← 每个标签触发 markDirty()

  }

```

**依赖关系图**：
```
tokens.dat (获取 userName)
    ↓
profiles.dat[userName] (获取用户信息)
    ↓
states.dat[userName] (恢复标签页)
    ↓
preferences.dat[userName] (恢复主题)
    ↓

```

**为什么必须串行**：
1. ✅ **userName 是 key** - 必须先知道用户名才能读取其他数据
2. ✅ **主题优先** - 必须先设置主题，避免页面闪烁
3. ✅ **状态依赖** - 菜单恢复依赖主题已设置

**但是有一个可以优化的点**：

```typescript
// ❌ 当前实现：循环调用，每次都触发 markDirty()

  menuStore.clearVisitedViews();

    menuStore.addVisitedView({  // ← 10 个标签 = 10 次 Zustand 更新
```

**问题**：
- 如果有 10 个标签页，调用 10 次 `addVisitedView()`
- 每次调用触发 `markDirty()` → 设置 3 秒防抖定时器
- Zustand 状态更新 10 次 → React 可能重新渲染 10 次

### 🔧 优化方案

#### 方案 A：并行解密文件（**推荐，效果最明显**）

**适用范围**：`initAllStorage()` 阶段

**原理**：5 个文件之间没有依赖关系，可以同时解密

```typescript
// ❌ 优化前：串行（500ms）
export async function initAllStorage(): Promise<void> {
  const files = ['app.dat', 'tokens.dat', 'profiles.dat', 'states.dat', 'preferences.dat'];
  
  for (const file of files) {
    const data = await loadAndDecrypt(file);  // ← 排队等待
    memoryCache.set(file, data);
  }
}

// ✅ 优化后：并行（100-150ms）
export async function initAllStorage(): Promise<void> {
  const files = ['app.dat', 'tokens.dat', 'profiles.dat', 'states.dat', 'preferences.dat'];
  
  // 同时解密所有文件
  const loadPromises = files.map(file => loadAndDecrypt(file));
  const results = await Promise.all(loadPromises);
  
  // 写入各自的内存缓存
  files.forEach((file, index) => {
    memoryCache.set(file, results[index]);
  });
}
```

**预期效果**：
- 从 500ms 降低到 100-150ms（**提速 3-5 倍**）
- 因为所有文件同时解密，而不是排队

**风险评估**：✅ **无风险**
- 5 个文件独立解密，没有交叉依赖
- 各自写入独立的 memoryCache key
- `initFromStorage()` 仍然在 `await initAllStorage()` 之后，保证数据已就绪

**实施时机**：可以在阶段一（创建 scheduler）时顺便修改

#### 方案 B：批量恢复状态（**减少 Zustand 更新次数**）

**适用范围**：`initFromStorage()` 阶段

**原理**：一次性恢复所有标签页，而不是逐个添加

```typescript

```

**预期效果**：
- 从 10 次 Zustand 更新降低到 1 次
- React 渲染次数从 10 次降低到 1-2 次
- 节省约 50-100ms

**风险评估**：🟡 **需要注意**
- `addVisitedView` 内部有 `noCache` 检查逻辑
- `restoreState` 需要处理这个逻辑
- 需要确保 `cachedViews` 正确设置

**实施时机**：需要修改 `menuStore.restoreState()` 方法

### 2. **保存调度器** (`scheduler.ts`)

```typescript
/**
 * 保存调度器
 * 职责：
 * 1. 管理多个独立的防抖定时器
 * 2. 根据策略决定保存时机
 * 3. 合并同一类型的多次变更
 * 4. 提供强制刷新接口
 */

import type { SaveType } from './strategies';
import { SAVE_CONFIG, SaveStrategy } from './strategies';
import { getStorageData, saveStorageDataAsync } from './core';
import { useAuthStore } from '@/stores/authStore';

class SaveScheduler {
  // 每个 SaveType 独立的防抖定时器
  private timers: Map<SaveType, number> = new Map();
  
  // 待保存的数据队列
  private pendingData: Map<SaveType, any> = new Map();
  
  /**
   * 调度保存任务
   * @param type 保存类型
   * @param dataBuilder 数据构建函数（延迟执行，获取最新状态）
   */
  schedule(type: SaveType, dataBuilder: () => any): void {
    const config = SAVE_CONFIG[type];
    
    // 记录待保存数据
    this.pendingData.set(type, dataBuilder);
    
    // 清除该类型的旧定时器
    const oldTimer = this.timers.get(type);
    if (oldTimer) {
      clearTimeout(oldTimer);
    }
    
    // 根据策略决定保存时机
    if (config.strategy === SaveStrategy.IMMEDIATE) {
      // 立即保存
      this.executeSave(type);
    } else {
      // 防抖保存
      const timer = window.setTimeout(() => {
        this.executeSave(type);
        this.timers.delete(type);
      }, config.debounceMs);
      
      this.timers.set(type, timer);
    }
  }
  
  /**
   * 执行保存
   */
  private async executeSave(type: SaveType): Promise<void> {
    const { userName, token } = useAuthStore.getState();
    if (!userName || !token) return;
    
    const dataBuilder = this.pendingData.get(type);
    if (!dataBuilder) return;
    
    try {
      const data = dataBuilder();
      await this.writeToStorage(type, userName, data);
      this.pendingData.delete(type);
    } catch (error) {
      console.error(`[Scheduler] ${type} 保存失败:`, error);
      // 失败时保留数据，等待下次调度
    }
  }
  
  /**
   * 写入存储
   */
  private async writeToStorage(
    type: SaveType,
    username: string,
    data: any
  ): Promise<void> {
    const existingState = getStorageData<Record<string, any>>('states.dat');
    const existingUserState = existingState[username] || {};
    
    const existingPrefs = getStorageData<Record<string, any>>('preferences.dat');
    const existingUserPrefs = existingPrefs[username] || {};
    
    // 根据类型决定写入哪个文件
    switch (type) {
      case 'tab':
      case 'snapshot':
      case 'route':
      case 'sidebar':
        // 写入 states.dat
        const newState = {
          ...existingUserState,
          ...data,
          lastSnapshot: Date.now(),
        };
        
        saveStorageDataAsync('states.dat', {
          ...existingState,
          [username]: newState,
        });
        break;
        
      case 'preference':
        // 写入 preferences.dat
        const newPrefs = {
          ...existingUserPrefs,
          ...data,
        };
        
        saveStorageDataAsync('preferences.dat', {
          ...existingPrefs,
          [username]: newPrefs,
        });
        break;
    }
  }
  
  /**
   * 强制立即保存指定类型
   */
  async flush(type: SaveType): Promise<void> {
    const timer = this.timers.get(type);
    if (timer) {
      clearTimeout(timer);
      this.timers.delete(type);
    }
    
    if (this.pendingData.has(type)) {
      await this.executeSave(type);
    }
  }
  
  /**
   * 强制立即保存所有待保存数据
   */
  async flushAll(): Promise<void> {
    // 清除所有定时器
    for (const [type, timer] of this.timers) {
      clearTimeout(timer);
    }
    this.timers.clear();
    
    // 依次保存所有待保存数据
    const types = Array.from(this.pendingData.keys());
    for (const type of types) {
      await this.executeSave(type);
    }
  }
  
  /**
   * 清理资源
   */
  dispose(): void {
    for (const timer of this.timers.values()) {
      clearTimeout(timer);
    }
    this.timers.clear();
    this.pendingData.clear();
  }
}

// 单例导出
export const scheduler = new SaveScheduler();
```

```typescript
/**
 * 自动保存兼容层
 * 保留旧的 markDirty() 接口，转发到新的 scheduler
 */

import { scheduler } from './scheduler';
import { SaveType } from './strategies';
import { useAuthStore } from '@/stores/authStore';
import { useMenuStore } from '@/stores/menuStore';
import { usePageStateStore } from '@/stores/pageStateStore';
import { useUserPrefsStore } from '@/stores/userPrefsStore';
import { getCurrentWindow } from '@tauri-apps/api/window';
import type { UnlistenFn } from '@tauri-apps/api/event';

let isInitialized = false;
let unlistenCloseRequested: UnlistenFn | null = null;

/**
 * 兼容旧的 markDirty() 接口
 * 转发到 snapshot 类型保存
 */
export function markDirty(): void {
  scheduler.schedule(SaveType.SNAPSHOT, () => {
    const menuState = useMenuStore.getState();
    const pageState = usePageStateStore.getState();
    
    const currentPath = window.location.pathname;
    const activeRoute = ['/login', '/force-two-factor', '/detached'].includes(currentPath)
      ? '/dashboard'
      : currentPath;
    
    return {
      visitedViews: menuState.visitedViews.map(v => ({
        path: v.path,
        name: v.name,
        title: v.title || v.meta?.title || '',
      })),
      cachedViews: menuState.cachedViews,
      sidebarCollapsed: menuState.collapsed,
      activeRoute,
      pageStates: pageState.pages,
    };
  });
}

/**
 * 强制立即保存（窗口关闭时使用）
 */
export async function forceSave(): Promise<void> {
  await scheduler.flushAll();
}

/**
 * 启动自动保存
 */
export async function startAutoSave(): Promise<void> {
  if (isInitialized) return;
  isInitialized = true;

  // 窗口关闭前强制保存
  try {
    const appWindow = getCurrentWindow();
    unlistenCloseRequested = await appWindow.onCloseRequested(async (event) => {
      event.preventDefault();
      await forceSave();
      await appWindow.close();
    });
  } catch (e) {
    console.warn('[AutoSave] 注册窗口关闭事件失败:', e);
  }
}

/**
 * 停止自动保存
 */
export function stopAutoSave(): void {
  if (!isInitialized) return;

  if (unlistenCloseRequested) {
    unlistenCloseRequested();
    unlistenCloseRequested = null;
  }

  scheduler.dispose();
  isInitialized = false;
}
```

## ⚠️ 风险与应对

### 风险 1：并发写入冲突
**问题**：多个 Manager 同时写入 `states.dat` 可能覆盖彼此数据

**解决方案**：
```typescript
// scheduler.writeToStorage 中合并现有数据
const existingState = getStorageData<Record<string, any>>('states.dat');
const existingUserState = existingState[username] || {};

const newState = {
  ...existingUserState,  // 保留已有的其他字段
  ...data,               // 只更新当前类型的字段
  lastSnapshot: Date.now(),
};
```

### 风险 2：内存泄漏
**问题**：定时器未清理

**解决方案**：
- `scheduler.dispose()` 清理所有定时器
- 窗口关闭时调用 `stopAutoSave()`
- 单元测试验证 dispose 逻辑

### 风险 3：向后兼容
**问题**：旧代码仍调用 `markDirty()`

**解决方案**：
- 保留 `autoSave.ts` 作为兼容层
- `markDirty()` 转发到 `scheduler.schedule(SaveType.SNAPSHOT, ...)`
- 逐步替换所有调用点

### 风险 4：性能问题
**问题**：频繁调用 `getStorageData()` 读取缓存

**解决方案**：
- `getStorageData()` 只读内存缓存，无 IO 开销
- Rust 端的 `saveStorageDataAsync` 是 fire-and-forget，不阻塞主线程
