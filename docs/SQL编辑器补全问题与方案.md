# SQL 编辑器补全性能问题与方案

状态：仅讨论阶段。本文件用于记录已确认的问题、代码核对结果和拟议方案。在下面的事项确认之前，不修改业务代码。

## 1. 目标行为

目标是实现类似 Navicat 的即时补全，而不是等用户停止输入后才补全：

- 每次 token 字符发生变化时都可以触发补全。
- 普通补全路径应尽量控制在约 50ms 内完成。
- 一旦确认当前 token 没有匹配项，同一个 token 后续继续变长时，应立即复用空结果。
- 负匹配路径不能重新扫描候选，也不能重复执行 fuzzyMatch。
- 空格、换行、分号、光标移动到其他 token、别名变化和元数据变化，都应创建新的上下文或版本。
- 删除字符时，如果条件允许，应回退并复用之前已经计算过的前缀级别。
- 匹配结果数量和 UI 最终显示数量必须分离。

## 2. 已核对的主要代码

主要涉及文件：

- `src/pages/Sql/Search/components/SqlEditor.tsx`：Ace 输入、delta 增量维护、补全触发、React 同步。
- `src/pages/Sql/Search/components/sqlEditorUtils.ts`：点号补全命令。
- `src/utils/sql/index.ts`：补全主流程、上下文处理、候选合并。
- `src/utils/sql/matcher.ts`：模糊匹配、去重、排序和截断。
- `src/utils/sql/prefixIndex.ts`：前缀索引、增量匹配、负结果链和前缀回退。
- `src/utils/sql/completionIndex.ts`：表索引和字段索引。
- `src/utils/sql/statementContext.ts`、`documentIndex.ts`、`parser.ts`：语句、表、别名和光标上下文解析。

## 3. 已确认的不匹配点

### 3.1 延迟触发不符合约 50ms 的目标

`SqlEditor` 当前关闭了 Ace 的实时自动补全，并在最后一次 change 事件约 180ms 后再调度 `startAutocomplete`。

这只能规避连续输入期间的重复计算，不能证明增量算法和负缓存逻辑是正确的，也不符合 Navicat 式的即时反馈目标。

最终方案应允许即时触发，并以约 50ms 作为性能预算：

- 负缓存命中：应接近 0ms；
- 普通增量过滤：尽量低于 5ms；
- 第一次完整扫描：控制在 50ms 以内；
- 只有结果真正发生变化时才更新补全弹窗。

### 3.2 `MAX_SUGGESTIONS = 1` 混淆了匹配数量和显示数量

`src/utils/sql/index.ts` 当前将 `MAX_SUGGESTIONS = 1` 传递给关键字、函数、数据库、表、字段和别名等匹配阶段。

这会导致每个候选类别最多只返回一项，匹配层在合并之前就被截断，造成两个问题：

1. 正常情况下无法保留多个匹配结果；
2. 最终排序和合并缺少完整候选集。

正确的职责应当分离：

```text
matchIncremental：保留完整的匹配结果集
最终 UI 层：根据 displayLimit 决定显示 10 条、20 条或其他数量
```

不能在每一个候选类别内部都硬编码限制为一条。

### 3.3 `null`、空数组和 Ace callback 中的 `null` 含义不同

在 `matchIncremental` 内部：

- `entries === null`：没有可复用的历史结果，需要进行第一次计算；
- `entries === []`：已经确认当前条件没有匹配，是一个有效的负缓存结果。

公开返回类型是 `Suggestion[]`，所以“无匹配”应以空数组表示，而不是 `null`。

另外，在：

```ts
callback(null, results)
```

这里的第一个 `null` 是 Ace callback 的 error 参数，表示没有错误；它不表示没有候选结果。

后续设计必须明确区分以下状态：

- `UNINITIALIZED`：尚未计算，需要完整计算；
- `MATCHED`：存在匹配结果，可以继续增量过滤；
- `NO_MATCH`：已经确认无匹配，后续更长前缀可以立即返回空结果；
- callback 无错误：这是回调协议的状态，不能拿来表示负缓存。

### 3.4 负增量路径已经存在，但只在同一作用域内生效

当前逻辑原则上已经可以实现：

```text
第一次前缀没有匹配 -> 保存 entries = []
后续前缀继续变长   -> 从之前的空 entries 继续过滤 -> 仍然得到 []
```

这基本符合期望的负缓存行为，但前提是以下条件保持稳定：

- `scopeKey` 不变；
- 新前缀确实是旧前缀的延长；
- 候选源的 identity 不变；
- fuzzy 策略状态没有变化；
- completer 实例没有被重新创建。

当前作用域包含编辑器实例、语句起始位置、token 起始位置、候选类别以及部分上下文信息。空格导致 token 起始位置变化并创建新作用域，这是正确行为。

### 3.5 候选源 identity 变化可能导致缓存失效，即使内容完全相同

`matchIncremental` 使用 `namesRef` 的引用进行候选源判断。如果数组内容没有变化，但每次都重新创建了数组，引用发生变化，缓存链仍会被重置。

目前需要重点观察：

- `tables` 数组引用是否稳定；
- 字段源数组引用是否稳定；
- 数据库名称数组引用是否稳定；
- completer 是否被重复创建；
- 元数据变化时是否通过明确的 candidateVersion 使缓存失效。

这是一个需要在真实输入链路中测量的潜在失效点，不能在没有诊断数据的情况下直接认定它就是根因。

### 3.6 某一个候选类别命中负缓存，不代表整个补全流程停止

即使关键字匹配已经命中负缓存，`createSqlCompleter` 仍然可能继续处理其他候选类别，包括：

- 函数；
- 数据库；
- 表；
- 当前语句可见表的字段；
- 别名；
- 最终候选合并；
- Ace 补全弹窗的布局和渲染。

因此，单个 `matchIncremental` 调用为 O(0)，并不等于整个补全请求为 O(0)。外层流程仍可能执行：

- 读取当前行；
- 定位当前语句；
- 解析上下文；
- 遍历可见表；
- 获取字段索引；
- 构造候选数组；
- 最终排序；
- 弹窗布局和渲染。

必须测量完整请求的耗时，不能只看某一个匹配函数。

### 3.7 第三个字符触发 fuzzy 策略切换是合理例外

当前逻辑主要是：前两个字符优先使用 `startsWith`，达到三个字符后可能开启 fuzzy 匹配。

因此下面的行为可能是合理的：

```text
ct  -> startsWith 没有结果
cti -> 重新执行一次 fuzzy 计算，可能匹配到 created_time
```

第三个字符导致一次匹配策略切换，不应简单视为负缓存失效。

但是策略切换完成后，如果结果仍然为空，那么：

```text
ctix
ctixx
ctixxx
```

应该稳定命中负缓存，不再进行完整候选扫描。

## 4. 长按输入卡顿的最可能原因

当前代码还不能证明“负缓存完全没有实现”。需要区分以下情况：

1. **重复请求仍在执行**：`completionGeneration` 可以丢弃旧请求的回调结果，但不能取消已经开始执行的同步计算。旧请求仍可能持续占用主线程。
2. **作用域或候选源发生变化**：`tokenStart`、`statementStart`、SQL 子句、数组引用、字段源或 completer 重建，都会导致缓存链重置。
3. **外层流程耗时**：上下文解析、可见表遍历、字段索引查询、候选合并和弹窗渲染，即使某个类别命中空缓存，仍然可能继续消耗时间。
4. **补全以外的耗时**：Ace 布局/绘制、React 同步、快照构建、`JSON.stringify`、IPC 参数复制和浏览器布局，都可能是真正的卡顿来源。

所以当前阶段不应直接把问题归结为“增量过滤算法失效”，必须先建立可观测证据。

## 5. 建议的讨论和实施顺序

### 第一步：定义 token 级状态机

每个候选类别都应有独立的 token session，建议使用以下信息作为缓存作用域：

```text
editorId + statementId + tokenStart + contextVersion + candidateVersion + candidateType
```

状态包括：

- `UNINITIALIZED`：没有历史记录，需要第一次完整计算；
- `MATCHED`：存在匹配结果，可以基于上一次结果继续过滤；
- `NO_MATCH`：当前 token 已确认无匹配，后续更长前缀直接返回空结果。

### 第二步：用诊断数据证明是否命中负缓存

在修改算法之前，先为每次补全请求记录以下信息：

- `scopeKey`；
- 当前 `prefix` 和 `previousPrefix`；
- `candidateVersion`；
- `cacheState`；
- 是否执行 `fullScan`；
- 是否执行 `fuzzyScan`；
- `filteredCount`；
- `resultCount`。

期望看到的序列是：

```text
第一次无匹配请求：fullScan = true
后续字符请求：  fullScan = false，filteredCount = 0
```

如果后续字符仍然出现 `fullScan = true`，再继续定位具体原因：

- 作用域是否变化；
- 候选源引用是否变化；
- fuzzy 策略是否发生切换；
- completer 是否被重新创建；
- 调用方参数是否发生变化。

### 第三步：在约 50ms 预算下恢复即时触发

不能继续依赖约 180ms 的延迟来掩盖重复计算。每个 token 字符变化都可以触发补全，但必须满足：

- 负缓存命中时几乎不做计算；
- 普通增量过滤只过滤上一次结果集；
- 第一次完整扫描有明确的耗时上限；
- 旧请求不能继续阻塞新请求；
- 补全结果没有变化时不重复更新弹窗。

### 第四步：分离匹配结果和显示结果

匹配 API 应保留完整候选集以及对应状态，最终 UI 层单独应用 `displayLimit`。

默认显示数量可以讨论为 10 条或 20 条，但匹配阶段不能再固定为一条。

### 第五步：明确缓存重置规则

- 继续输入当前 token：复用当前 session；
- 删除最后一个字符：尽量回退到历史前缀级别；
- 空格、换行、分号：创建新的 token 或语句上下文；
- 光标移动到其他 token：切换 session；
- 别名变化：增加 `contextVersion`；
- 元数据变化：增加 `candidateVersion`。

## 6. 实施前需要确认的问题

1. 是否恢复每次字符变化都触发补全，并以约 50ms 作为普通路径预算？
2. 是否将“无匹配”建模为明确的负缓存状态，不再混用 `null`、空数组和 callback error 参数？
3. 是否在匹配层保留多个结果，并由 UI 层单独限制显示数量？默认显示 10 条还是 20 条？
4. 是否采用按编辑器、语句、token、上下文版本、候选版本和候选类别划分的 token session？

以上问题确认后，再开始统一实施。

## 7. 与保存链路的边界

后端异步保存可以减少前端等待加密和磁盘写入的时间，但不能消除前端快照构建、`JSON.stringify` 或 IPC 参数复制的耗时。

补全性能和保存性能应分别测量。将完整 `states.dat` 快照拆分为增量 patch，是后续独立的优化方向，不应与当前补全负缓存问题混在一起处理。

## 8. 当前结论

目前已经确认三个直接不匹配点：

1. 当前约 180ms 的延迟触发，不符合约 50ms 的即时补全目标；
2. `MAX_SUGGESTIONS = 1` 混淆了匹配层和显示层职责；
3. `null`、空数组和 Ace callback 中的 `null` 含义不同，当前日志无法直接证明是否命中了负缓存。

同时，`matchIncremental` 已经具备将空结果继续传递给更长前缀的基础能力。

因此下一步不应该立即重写缓存算法，而是先证明真实输入链路是否因为作用域变化、候选源 identity 变化、策略切换或重复请求而失去缓存命中。确认原因后，再分离匹配层与显示层，并恢复真正的即时触发。
